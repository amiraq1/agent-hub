# ADR-001: اعتماد Git كمخزن حالة مشترك

**الحالة:** معتمد (Accepted)  
**التاريخ:** 2026-11-19  
**المقررون:** عمار محمد، Muse، وكلاء نبض  

---

## السياق (Context)
يعمل وكلاء منظومة "نبض" عبر بيئات تشغيل موزعة جغرافياً وتقنياً (وكيل سحابي، وكيل على خادم Cue، ووكيل تطوير محلي). لا توجد مساحة ملفات مشتركة بين هذه البيئات، وتتطلب المرحلة التأسيسية إثبات جدوى حلقة التنسيق المشتركة دون تكاليف استضافة أو تعقيدات تشغيل قواعد بيانات وخوادم وسيطة مبكرة.

---

## القرار (Decision)
تقرر اعتماد **Git ومستودع GitHub كمخزن مركزي موحد للحالة (State Store)** عبر ملف `agents-state.json` في الفرع الرئيسي:

1. **الوصول المباشر:** تقرأ اللوحة الساكنة (GitHub Pages) ملف الحالة علناً عبر الرابط المباشر دون الحاجة لمصادقة أو خوادم خلفية.
2. **التحديث غير المتزامن:** يحدّث الوكلاء حالاتهم ومهامهم عبر طلبات سحب (Pull Requests) أو التحديث المباشر للملف مع التحقق الآلي في CI.
3. **تجريد البيانات الحساسة:** يُمنع تخزين أي مفاتيح أو أسرار داخل الملف ليظل المستودع واللوحة عامين وآمنين.

---

## النتائج والتبعات (Consequences)

### الإيجابيات:
- **صفر بنية تحتية وتكاليف:** لا حاجة لخوادم أو قواعد بيانات في مرحلة الانطلاق.
- **سجل تدقيق تاريخي طبيعي:** توفر سجلات Git وCommits أرشيفاً موثقاً لكل تعديل وسببه والطرف الذي أجراه.
- **بساطة الصيانة:** يعتمد التحقق على سكربت Node.js مستقل يعمل عبر GitHub Actions.

### التحديات والمخاطر:
- **زمن الاستجابة غير لحظي:** يرتبط التحديث بدورة Git وتحديث الروابط الخام (Raw Cache).
- **مخاطر تعارض التعديلات المتزامنة:** تعالج حالياً عبر التسلسل المنطقي والتنسيق عبر البريد، ولاحقاً بنظام حجز المهام (Leases).

---

## شروط الانتقال إلى API وقاعدة بيانات مخصصة
يتم الانتقال من نمط Git إلى خادم API وقاعدة بيانات (مثل Supabase) عند تحقق أحد الشروط التالية:
1. وصول عدد الوكلاء أو تكرار النبضات إلى حد يسبب تعارضات متكررة في Git.
2. الحاجة إلى استجابة لحظية بأجزاء من الثانية.
3. الانتقال إلى المرحلة 3 وتوفير مساحات عمل متعددة (Multi-tenant) مع عزل صلاحيات وصلاحيات وصول خاصة (RLS).
